Finding

This review identifies a P1 performance defect in `billing/history.py`. The billing history endpoint performs N+1 reads: it first loads the invoice set and then issues a separate line-item query for each invoice row. That access pattern makes database work grow directly with the number of invoices returned, instead of retrieving the required history in a bounded query plan. Because this is a billing endpoint and the amplification occurs on a normal tenant request, the issue should be treated as an urgent production risk rather than routine optimization work. Larger histories will place disproportionate load on the database, increase endpoint latency, and consume connection capacity that may affect other requests sharing the same database.

Evidence

The reviewed flow loads invoices once, then performs one line-item query per row. The fixture gives a concrete case: a tenant with 400 invoices causes 401 reads. One read obtains the invoices, and 400 additional reads obtain their line items. This behavior is the defining N+1 pattern and shows that the cost is already material at a plausible tenant size. The relevant query filters by `tenant_id` and `created_at`. The database engine supports a composite index on those columns, so the filter can be served by an index aligned with the query rather than relying on a less selective access path. These facts support the P1 classification: the endpoint combines multiplicative query volume with a filter that is not yet described as having the available composite index.

Recommendation

Remove the per-row lookup by fetching line items in bulk for the invoices returned, or by using the repository’s existing eager-loading or join mechanism if one is already available. Keep the change local to the current data-access path; a new abstraction or dependency is unnecessary. Add a composite index on `tenant_id` and `created_at`, with column order confirmed against the actual query and database execution plan. The query rewrite and index address different costs: bulk retrieval eliminates the N+1 reads, while the composite index improves how the filtered invoice set is located. Validate the result with a focused test that asserts query count does not scale with invoice count, and compare the execution plan before and after adding the index. Also exercise the 400-invoice case to confirm that it no longer produces 401 reads and that response contents remain unchanged.
